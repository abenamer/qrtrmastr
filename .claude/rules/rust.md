# REAS rules for Rust

The project follows the REAS standard, version 1.9.0-draft, vendored at `standards/reas/` (its documents under `standard/`, its example packages under `examples/`). Each rule has an identifier and one shape: Intent, Enforcement, Scope, Rules, optional Allowances, Verification, optional Limits. Read the file named for the full text before you apply a rule, read its Scope first, and cite the identifier when a decision rests on it. The lines below are the requirements the standard states, condensed. They do not say what the project meets: the [self-audit](../../docs/self-audit.md) lists each rule with its status, and [ADR 0015](../../docs/decisions/0015-reas-1-7-0-draft-and-the-order-of-its-gaps.md) gives the order in which the gaps close. Do not make a gap larger: new code follows the rule even where old code does not yet.

## Foundations (`standards/reas/standard/foundations.md`)

- **REAS-FOUND-001, raise the floor, hold the ceiling.** Advisory. Do not defer a known engineering responsibility because it can be done later. Do not add a type, a trait, a layer or a test because it is cheap to generate: a recorded requirement or an existing responsibility needs it.
- **REAS-FOUND-002, no foreseeable rework.** Do not choose a temporary or deficient implementation when a maintainable one is practical and its requirement is recorded. Make the decisions that are costly to reverse, or that later code copies, deliberately and early.
- **REAS-FOUND-003, the first instance is the template.** The first instance of a pattern is the one that is copied. When a copied pattern is wrong, correct the template and the copies in one change.
- **REAS-FOUND-004, apply by property, scale by consequence.** A property of the system decides whether a check applies. The consequence of a failure, at the component, decides how much of it runs. A component is consequential when one defect in it can expose sensitive data, misuse a credential that can change or spend, lose money, or cause physical, legal or safety harm, through a failure path that the maintainer can name. A session proposes the failure path; the maintainer records the judgment. A component that handles outside data, credentials or money with no recorded judgment is treated as consequential. Recorded here on 2026-11-22 (ADR 0001, ADR 0020): the redactor and the Gmail adapter are consequential. The redactor is gone since 2026-11-27 (ADR 0021), so the Gmail adapter is the one consequential component; a new component has no judgment until the maintainer gives one.
- **REAS-FOUND-005, a check is not an investigation.** A pass is reported with its outcome and its evidence. A finding says in a few sentences what failed, why it matters, how sure the evidence is, whether it needs intervention, and what stays uncertain. A possible deeper inquiry is a recommendation to the maintainer, not work that a session starts.

## Core Rust (`standards/reas/standard/core-rust.md`)

- **REAS-RUST-001, invariants explicit.** Newtypes with private fields and smart constructors for domain values with invariants; deserialization goes through the same validation; `Option` for optional, `Result` for fallible; enum variants for the legal cases, matched without a wildcard arm for enums this project controls. Lint: `clippy::wildcard_enum_match_arm` at `deny`. One rejection test for each invariant, through the constructor and through the deserializer.
- **REAS-RUST-002, abstractions for the reader (advisory).** Pick the abstraction that makes the code path easy to follow, then measure its runtime cost; explain any abstraction with extra runtime cost; never remove one only to compile faster.
- **REAS-RUST-003, trait relationships explicit.** A blanket implementation only when it is correct for every type that meets its bounds; no generic repository framework before a second concrete implementation exists; no inherent method named like a trait method on the same type. Lint: `clippy::same_name_method` at `deny`.
- **REAS-RUST-004, ownership explicit.** Make the owner of each value easy to find; `&str`, `&[T]`, `&Path` for a value the function only reads, ownership when it stores the value; no clone only to satisfy the borrow checker; `Arc<Mutex<T>>` only for shared ownership with synchronised mutation. Lints: `clippy::needless_pass_by_value` and `clippy::redundant_clone` at `warn`. Test code is out of scope.
- **REAS-RUST-005, errors explicit.** The library returns `Result` with a typed error: one enum for each module surface, one variant for each cause a caller can act on, the lower error kept with `#[source]` or `#[from]`; no `anyhow::Error` in the library's public API. The binary adds context with `anyhow` and returns a failure status. Panic only for a bug; no `unwrap` where `None` or `Err` can occur; `expect` with the reason when failure is impossible; no default in place of a missing required input. Lints: `clippy::unwrap_used` at `deny`, `clippy::expect_used` at `warn` with `#[expect]` and a reason on each accepted use. Each error variant has a test that produces it. Test code is out of scope.
- **REAS-RUST-006, compile after each step.** `cargo fmt --all`, `cargo check --all-targets`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, and `RUSTDOCFLAGS="-D warnings" cargo doc --no-deps` after each change to a type, function, module, manifest or lint setting; report only the checks that ran. Lint levels are declared once under `[lints]` in `Cargo.toml`. Suppress a lint with `#[expect(lint, reason = "...")]`, never `#[allow]`. Lints: `clippy::allow_attributes` and `clippy::allow_attributes_without_reason` at `deny`.
- **REAS-RUST-007, async and CPU work apart.** No blocking I/O or CPU work on an executor thread: `spawn_blocking` or a bounded pool, with a limit on concurrent work; never hold a `std::sync::Mutex` guard across an `.await`; record how a task responds to cancellation and shutdown.
- **REAS-RUST-008, money exact.** Money is integer minor units in a type that carries the currency, or a decimal type with a named rounding mode where the arithmetic divides or applies a rate; checked arithmetic with a typed error on overflow; no `f32` or `f64`, no bare `i64`; `NUMERIC` or integer minor units in PostgreSQL, converted at the adapter. Lint: `clippy::float_arithmetic` at `deny` in each module that handles money. Tests: rounding at the half-unit boundary, overflow, currency mismatch. Here: `domain::money::Money` is a decimal with a `Currency`; its arithmetic is checked and has no saturating form; `clippy::float_arithmetic` is `deny` for the whole package.
- **REAS-RUST-009, public items documented.** A `///` comment on each public item; `# Errors` naming each variant and its cause on a fallible function; `# Panics` on a function that can panic; the documentation builds with warnings denied. Lints: `missing_docs`, `clippy::missing_errors_doc`, `clippy::missing_panics_doc`; this project sets them to `deny`. A comment is a claim about the code: read the function and what it calls before you write when it fails, and what a library does before you say so. In `src/adapters/cli/mod.rs` a doc comment is the help text of the command.

## State machines (`standards/reas/standard/state-machines.md`; the typestate example is `standards/reas/examples/typestate/`)

- **REAS-STATE-001, runtime states.** One enum per workflow state, never several Boolean flags; each legal transition is a function; a typed error for a transition the state does not permit; match every variant; one test for each legal and each refused transition.
- **REAS-STATE-002, typestate (advisory).** Where operation order, initialisation or a verification step is an invariant: the handler takes the verified state type only, and only the function that does the check constructs it. State from a file, a database or the network is a runtime enum, validated at run time; this project keeps persisted state in `domain::states`.
- **REAS-STATE-003, persisted transitions.** A conditional update (`... WHERE id = $1 AND parse_state = $2 AND version = $3`) for each transition; success only when exactly one row changed; a conflict otherwise. The expected version is a fencing token. `raw_messages.parse_state` with its `version` column is the pattern. Test: two writers, exactly one succeeds, against PostgreSQL.

## Architecture (`standards/reas/standard/ports-and-adapters.md`; the example is `standards/reas/examples/ports-and-adapters/`)

- **REAS-ARCH-001, visible code path.** Inbound adapter, application use case, port trait, outbound adapter; one composition root (`src/main.rs`); a use case may call a port directly; no forwarding layer without a different responsibility.
- **REAS-ARCH-002, dependencies inward.** SQLx, file and network types and the clock stay out of `src/domain`; ports are declared in `src/application/ports.rs` and implemented in `src/adapters`. The inbound adapter is the trust boundary.
- **REAS-ARCH-003, the seven questions.** Who reads and maintains the code, what external systems it uses, how long it stays in use, how likely the boundaries are to change, who can supply outside data, which decisions are costly to reverse or will be copied, and which components are consequential, with a failure path of one sentence for each. The fifth answer sets the exposure for the security rules. The seven answers are in ADR 0001. The sixth lists eight decisions that are costly to reverse (the redaction before storage, the message key, the schema, the three layers, the form of a receipt parser, the sign-in to Gmail, the date library, the names of the keys of `[redaction]`): ask the maintainer before a change to one of them; when one changes, change the record. Do not decide the exposure yourself: ask the maintainer.
- **REAS-ARCH-004, concrete implementations visible.** A port only where a test double or a replaceable implementation is needed or to isolate a system outside our control; each port method in the application's terms, domain types in, domain types or a typed error out; a method that mirrors the storage API is an adapter in disguise; no factories of factories, no service locator, no duplicate interfaces; adapters named for what they adapt (`PostgresStore`, `TakeoutExport`).
- **REAS-ARCH-005, rules apart from infrastructure (advisory).** Business rules and mathematics are pure functions that take time, randomness and data as inputs; serialisation, row mapping and API clients live in adapters; dependencies come through constructors.
- **REAS-ARCH-006, adapter parameters (advisory).** A use case takes its adapter as a type parameter bound by the port by default; a trait object (`Arc<dyn Port + Send + Sync>`) where the implementation must vary at run time, with the decision recorded at the composition root; check dyn-compatibility first.

## Persistence (`standards/reas/standard/persistence.md`)

- **REAS-DATA-001, explicit storage.** One specific SQL query per operation, in a named adapter; every schema change is a migration; serde and SQLx attributes (`default`, `rename`) on the row or wire type in the adapter, never on a domain type (here: the wire types of `qm due --json` are in `src/adapters/cli/wire.rs`, a new field of a report is added there by hand, and `scripts/check.sh layers` fails when `src/domain` or `src/application` names serde or SQLx); database constraints for the invariants PostgreSQL can express; parameterised queries; an index only for a measured query, with the query it serves recorded.
- **REAS-DATA-002, transaction boundaries.** Writes that must succeed or fail together in one transaction, declared as one port operation whose adapter owns commit and rollback; no SQLx transaction types in domain or application code; no external side effects inside a database transaction's guarantee. Test: fail the second write, assert the first was rolled back.
- **REAS-DATA-003, data outlives the container.** Named volumes, backups outside the volume, a tested restore with its date recorded; never `docker compose down -v` against data to keep.
- **REAS-DATA-004, reproducible builds.** `Cargo.lock` committed and `--locked` in CI; no compile-time dependency on a developer's database; `cargo sqlx prepare --check` against a new database in CI; the Rust toolchain recorded.
- **REAS-DATA-005, idempotent consumers.** Each event has a stable identifier; the consumer records what it handled in the same transaction as the effect, or the effect is an upsert keyed by the identifier; never deduplicate on payload equality. Here the event is a mail and its identifier is the message key. Test: deliver the same event twice, assert one effect.

## Security at seams (`standards/reas/standard/security.md`; the example is `standards/reas/examples/trust-boundary/`)

Outside data is data a party other than this application wrote: mail, an answer from the Gmail API, and a stored message or order read back from the database. Each rule scales by the exposure that ADR 0001 records.

The Privacy section of `CLAUDE.md` wins over a line below. One place where that matters: a value taken from a mail is never logged, also not as the rejected value that REAS-SEC-002 sends to the log. The program stores no subject and no body of a mail (ADR 0021); what a parser extracts from a receipt is still encoded at each sink.

- **REAS-SEC-001, security properties.** Credentials out of source and logs; limits on size, count and time, each applied before the allocation or work it bounds; `cargo deny check` on each pull request and on a daily schedule; dependency sources restricted in `deny.toml`; `cargo vet` with the audits of organizations that the project names, and `cargo vet check` in CI; an own review, recorded, only for a build script or a proc-macro that no trusted audit covers and for a finding that stays open an imported audit stands in only when its criteria cover what the dependency does in the build, its source is one that the project trusts and has recorded, and it covers the exact version; a rise of the unsafe count of a dependency is closed by a trusted audit of the new version, or by an own review when no audit covers it and the dependency is on a path of outside data or in a consequential component; prefer a version that is more than a few days old. The project does not use `cargo vet` yet (line 19 of ADR 0019; the maintainer named Mozilla, Google and the Bytecode Alliance as the sources, and decides about each package that no audit covers before it is exempted), so no trusted audit exists here: each new dependency with a build script or a proc-macro gets a recorded own review before it is added; a recorded design review before a component that handles personal data or credentials is written.
- **REAS-SEC-002, parse at the trust boundary.** Parse outside data into domain types once, in the inbound adapter; port methods and domain functions take validated types only, not `String`, `Vec<u8>` or `serde_json::Value` for a value with an invariant; decode the transport, verify the origin, then parse the payload; no `Deserialize` derived on a type with an invariant (`#[serde(try_from = ...)]`); `#[serde(deny_unknown_fields)]` for a closed schema. A validation failure tells the caller what failed with no internal detail; the log gets the rule and the encoded value.
- **REAS-SEC-003, sizes once, with checked arithmetic.** A length, count, offset or index from outside data: `usize::try_from`, compared with its limit before the allocation or loop; `checked_add`, `checked_mul`, `checked_sub`; computed once; `get(start..end)`, never `[start..end]`. `overflow-checks = true` in the release profile. Only the linear-time `regex` engine on outside data, with `size_limit` on each such pattern. Lints: `clippy::arithmetic_side_effects` and `clippy::indexing_slicing` at `deny`; this project sets them, and `clippy::string_slice`, for the whole package in `Cargo.toml`. A lint that you add to `Cargo.toml` gets a planted violation in `examples/lint_canary.rs` and a line in `LINT_LEVELS` of `scripts/check.sh` in the same change. A pattern of the source goes through `domain::pattern::fixed`; a pattern built from data sets `domain::pattern::SIZE_LIMIT` itself. The lints do not see the index of a capture group: index only a group that takes part in every match.
- **REAS-SEC-004, unsafe confined.** `unsafe_code = "forbid"` under `[lints.rust]`. The program has no unsafe code. The one `unsafe` block of the repository is a planted violation in `examples/lint_canary.rs`, behind a flag, and the compiler refuses it there too. The Miri and sanitizer runs are in REAS-NATIVE-004 since 1.7.0-draft.
- **REAS-SEC-005, duplicate implementations.** A fast path or a cache keeps the simple implementation as the reference and has a differential test against it. This project has no duplicate implementation; the rule applies when one appears.
- **REAS-SEC-006, encode on output.** Validate on input, encode on output, in the adapter that writes to the context: HTML text and attribute, URL component, JSON string, SQL (parameters; quoted identifiers), log line and HTTP header (no control characters or line breaks). Do not sanitize on input. One test for each sink with that sink's special characters.

## Native code (`standards/reas/standard/native-code.md`)

Native code is code where the language's guarantees no longer hold: an `unsafe` block, an `extern` block or a `-sys` crate, a `core::arch` intrinsic, inline assembly, and a dependency that contains any of these on a path that outside data reaches. This project writes none. It depends on some: the TLS library uses `ring`, a Rust crate with C and assembly parts. The dependencies on a path of outside data (the mail parser, the HTML parser, the archive reader, the pattern engine and what they use) are counted in `unsafe-baseline.tsv` and listed in `docs/reference/native-code.md`; none of their unsafe code is reviewed. To add a tool, a toolchain or a CI job for these rules is the maintainer's decision: the lines below say what the standard asks, not what to install or run.

- **REAS-NATIVE-001, recognize the boundary (advisory).** A crossing into native code is an event: bound it, mark it, exercise it, the same way each time. Before you write native code, say why safe Rust cannot express the operation; a reviewed crate with a safe API usually can. A pull request that adds native code, or a dependency that brings it onto a path of outside data, says so.
- **REAS-NATIVE-002, bound the unsafe surface.** Here: `unsafe-baseline.tsv` is the baseline, `scripts/check.sh unsafe` compares the count of `cargo geiger` 0.13.0 with it in the `rust` job, and a change of `Cargo.lock` writes the baseline again in the same change (`scripts/check.sh unsafe write`), with a reason in the log for a count that grew. The rule keeps two counts: the count of the project's own crates is a committed baseline that may shrink or stay, and the count of each dependency is reported and compared with the run before, where a change is a review event and not a build failure, and a rise is a finding that a trusted audit or an own review closes (REAS-SEC-001); a growth of the count of an own crate needs a justification comment on the line, a review and an allowlisted module. Here one baseline holds both, and a change of either fails the group (ADR 0020). For this package the count is zero by `forbid`, and the rule asks that the zero is recorded; the dependencies on a path of outside data are counted too.
- **REAS-NATIVE-003, confine and mark.** `unsafe_code = "forbid"` in every crate. If unsafe code is ever needed: one small module with a safe API that checks each precondition, a `SAFETY` comment before each block, one operation in each block.
- **REAS-NATIVE-004, exercise it.** A fuzz target with property assertions for every parser of outside bytes (REAS-TEST-003); Miri on a module with unsafe; a path that Miri cannot execute (FFI, a vendor intrinsic, assembly) is marked Miri-blind and covered by a sanitizer build on hardware that has the feature; the record says which hardware ran.

## Validation and evidence (`standards/reas/standard/validation.md`)

- **REAS-TEST-001, invariants and failures.** Unit tests for each invariant and each transition, for error paths and invalid input; a failing test double for error propagation through a port; integration tests against the real PostgreSQL, never an in-memory stand-in. Each test is non-vacuous: a do-nothing change fails it; a negative assertion has a positive control on the same fixture; it calls the production entry point. For each `<`, `<=`, `>`, `>=` guard: below, at and above the threshold. Assert the typed variant and the diagnostic facts that its message must carry; pin exact wording only when the wording is a requirement. No test of a constructor or accessor alone. For decision code in a consequential component (REAS-FOUND-004; here the Gmail adapter): `cargo mutants --in-diff` before review, with `--jobs 1` when `DATABASE_URL` is set (the maintainer said on 2026-11-22 to make it a step of the protocol for these two; run it from now on; a missed mutant that no test kills and that is not equivalent goes to the maintainer in the pull request, and a session does not accept a survivor itself), and each missed mutant gets one of three outcomes in the pull request: killed, equivalent, or accepted survivor. An accepted survivor is only for a configured value that no external contract, no documented operational requirement and no correctness or security invariant fixes, where the tests show that the behaviour is correct for the configured value; it stays visible with its reason and is never reported as killed or equivalent. Elsewhere the pass is Advisory. Survivors are reported, not a score.
- **REAS-TEST-002, observable evidence.** Six outcomes, reported apart: passed, failed, errored, timed out, skipped, not run. A retry is reported with its attempts. A check over an empty population is not run. Each passed check has its date and commit or workflow run; a passing result does not carry over to code changed since. For a check with no pass criterion, such as a mutation pass, the result of the tool and the maintainer's disposition are two statements.
- **REAS-TEST-003, fuzz the adapters that read outside bytes.** One `cargo fuzz` target for each inbound adapter and parser that reads bytes from another party, calling its public entry point and asserting properties; a committed seed corpus; a run of 30 to 60 seconds for each target on each pull request from the kept corpus, with a report of the executions, the size of the corpus and whether the run reached its end; a longer campaign for a consequential component, recorded with its duration, its hardware and its reason; found inputs and crash artifacts kept in artifact storage or a corpus repository, the corpus made small on a schedule, a regression test for each crash; debug assertions and overflow checks on in the fuzz build; each architecture where the code has SIMD paths or paths that depend on the byte order. Here: the six targets are in `fuzz/` (ADR 0017; the target of the redactor went with it); a new reader of outside bytes gets its target, its seed in `scripts/fuzz_seeds.py` and its name in `FUZZ_TARGETS` of `scripts/check.sh` in the same change; a finding is corrected in the reader with a test in the program, and a property is not made weaker to pass; a target and a seed use made-up values, never a real term or a real mail.
- **REAS-TEST-004, doubles only at ports.** A test replaces a collaborator only where control leaves the application: the database, the mail source, the network, the clock, randomness. Code this application owns runs for real, including parsers and domain rules. Assert outcomes, not which methods a double received.
- **REAS-TEST-005, triage a failing test first.** Classify it as stale, patchwork or valid before you change it or the product. For a valid test, fix the product; never weaken, skip, retry to green or delete it. A changed or deleted test names its class and the coverage that replaces it in the commit message.

## Documentation (`standards/reas/standard/documentation.md`)

- **REAS-DOC-004, requirements in decisions.** A requirement in an ADR names its trigger and its observable response: "The system shall", "When <trigger>, the system shall", "While <state>, the system shall", "If <condition>, then the system shall".
- **REAS-DOC-006, a check where a check can exist.** A rule that can be checked mechanically gets a lint setting, a checker gate or a CI job, with a floor (a gate that scans nothing fails) and a planted-violation test. When a defect class comes back, add the check; do not add another reminder.
