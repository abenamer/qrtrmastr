# Build scripts and procedural macros of the dependencies

A dependency with a build script or a procedural macro runs code on the machine that builds `qm`: your machine, and the runner of CI. REAS-SEC-001 asks that this code is reviewed before the dependency is added, and that the review is recorded. Each dependency below was in the graph before a review existed, so this page is the first record, written after the fact.

The lockfile names 72 such packages: 50 with a build script and 24 with a procedural macro, two of them with both. 45 are compiled on Linux for x86_64, 43 for `qm` and 2 for its tests only. The other 27 are for another platform or for a feature that is off, and their code was not read.

## The result

* No build script fetches a file, opens a connection, or runs a program that it fetched or made.
* The programs that a build starts are: the compiler, for a question about its version or for a short probe (17 packages); the C compiler and the archiver, for `ring`; `rustfmt`, for `web_atoms`; and `cargo`, for the macro of `rstest`, in the test build only.
* Each of these programs is found through the environment: `RUSTC`, `RUSTC_WRAPPER`, `CC`, `AR`, `CARGO` and `PATH`. A process that can set a variable of the build can name another program. That is true for cargo itself too.
* One package carries programs that are already built: `ring` has 17 object files for Windows, which a build for Linux does not link.
* One macro can open a connection: the query macros of SQLx connect to a database while the program compiles, when a database URL is set and `SQLX_OFFLINE` is not. The project calls none of them. The macro that it calls, `sqlx::migrate!`, reads the files of `migrations/`.

When a dependency with a build script or a procedural macro is added, or one of the 45 moves to a new version, read its script or the changes of it, and add to this page in the same change. `cargo metadata` names the packages: a target of the kind `custom-build` or `proc-macro`.

## What a reader should look at

- **web_atoms 0.3.0 (build script, qm) starts `rustfmt`.** Its build-dependency string_cache_codegen 0.11.2 runs `Command::new("rustfmt")` (found through `PATH`) three times and pipes the generated Rust source through it (`lib.rs` lines 165 to 204 of string_cache_codegen). When `rustfmt` cannot start or exits with an error, the unformatted text is written. The result goes to `OUT_DIR/generated.rs`, which the library includes. No environment variable selects the program; `PATH` does.
- **rstest_macros 0.28.0 (proc-macro, tests only) starts `cargo` and reads the project's `Cargo.toml`.** Each `#[rstest]` expansion calls proc-macro-crate 3.5.0 (feature `crate-name`, on by default). That crate runs `$CARGO locate-project --workspace --message-format=plain --manifest-path=<project>/Cargo.toml` (first call in each compiler process) and reads `<project>/Cargo.toml` (`fs::metadata`, `fs::read_to_string`). The program is the one that the `CARGO` variable names. The macro also reads `RSTEST_TIMEOUT`. The project has 4 `#[rstest]` uses (in `src`, test code).
- **rstest_macros 0.28.0: `#[files("...")]` reads the file system at compile time.** It globs from `CARGO_MANIFEST_DIR` or from `#[base_dir = "..."]` (an absolute path is accepted), replaces `$VAR` and `${VAR}` in the pattern with environment variables, canonicalizes the paths, and can emit `include_str!` or `include_bytes!` of each file found. The project has 0 uses of `#[files]`.
- **sqlx-macros 0.9.1 (proc-macro, qm; the code is in sqlx-macros-core 0.9.1): the query macros can open a database connection at compile time. The project calls none of them.** Search of `src` and `tests`: `query!`, `query_as!`, `query_scalar!` and the `query_file` forms have 0 matches. If one is added, each expansion does this: reads `CARGO_MANIFEST_DIR`; checks `<project>/sqlx.toml`; runs `$CARGO metadata --format-version=1 --no-deps` in the project directory; reads `.env` in the project directory and in each parent directory up to the workspace root (with dotenvy); reads `DATABASE_URL` (or the name that `sqlx.toml` gives), `SQLX_OFFLINE` and `SQLX_OFFLINE_DIR` from the environment first and from `.env` second. It connects to the database when `SQLX_OFFLINE` is unset or false AND the database URL is set and not empty (`query/mod.rs` lines 81 to 88, `database/mod.rs` line 79). Otherwise it reads `query-<sha256>.json` from `SQLX_OFFLINE_DIR`, `<project>/.sqlx` or `<workspace>/.sqlx`. When it connects and `SQLX_OFFLINE_DIR` is set, it deletes and writes `query-<sha256>.json` in that directory.
- **sqlx-macros 0.9.1: the macros that the project does call read project files, and do not connect.** `sqlx::migrate!("./migrations")` (1 call, `src/adapters/postgres/mod.rs` line 14) reads `CARGO_MANIFEST_DIR`, checks whether `<project>/sqlx.toml` exists, lists `<project>/migrations` and reads each `.sql` file to compute its checksum, then emits `include_str!` with the absolute path of each file. `#[sqlx::test(migrations = false)]` (20 uses, `tests/database.rs`) checks whether `<project>/sqlx.toml` exists and reads nothing else at compile time; the database connection of these tests is made when the tests run, not when they compile. `#[derive(sqlx::FromRow)]` (4 uses) reads no file and no variable. `<project>/sqlx.toml` and `<project>/.sqlx` do not exist today.
- **sqlx-macros 0.9.1 links a large dependency set into the compiler process.** From `Cargo.lock`, its dependency closure has 193 packages, among them ring 0.17.14 (C and assembly), rustls 0.23.46 and libc 0.2.191. `Cargo.lock` lists every possible dependency; some are not enabled.

- **libc 0.2.191 (build script, qm) contains two more process calls that do not run for Linux.** `Command::new("freebsd-version")` runs only when the target OS is FreeBSD and `LIBC_CI` is set. `Command::new("emcc")` (or `emcc.bat`) with `-dumpversion` runs only when the target OS is emscripten.
- **Environment variables that name the program to start.** `RUSTC` (cargo sets it): every script in the table that starts the compiler runs this program. `RUSTC_WRAPPER`: anyhow, libc, proc-macro2, rustix, rustversion, thiserror, num-traits (through autocfg), rstest_macros (through rustc_version) run the wrapper with `rustc` as its argument. `RUSTC_WORKSPACE_WRAPPER`: anyhow, proc-macro2, thiserror, num-traits (through autocfg). Cargo passes these variables to build scripts and uses the same ones for its own compiler calls. `CARGO`: rstest_macros (through proc-macro-crate) and the sqlx query macros.
- **Not read line by line.** (1) The sources of the 18 proc-macro crates, about 53,000 lines, of which derive_more-impl is 12,424, rstest_macros 11,685, serde_derive 8,975 and clap_derive 4,577. I searched every `.rs` file outside `tests`, `examples` and `benches` with fixed patterns (listed in "How this was read"), read each match in context, and read in full the files named there. (2) cc 1.11.2, the helper of the ring build script: searched for process calls and variable names, not read in full. (3) The C, assembly and Perl sources of ring, and the content of its 17 object files: not read. (4) sqlx-core and sqlx-postgres beyond the config-file and migration-directory functions: not read. Reason in each case: size; the pattern search was the method.

Build scripts (29: the 27 "build script" rows and the 2 "both" rows):
- For each package I read the `build` key of `Cargo.toml` to find the script, and `[build-dependencies]`.
